## 2. 这个数放在文献里看

计算复现衰减的基准率很难看：27,271 个生物医学 Jupyter notebook，依赖装得上的
10,388 个里只有 879 个产出相同结果——**约 3.4%**；IR 那项研究发现四年后多数产物
在现代环境已无法运行。

**但两者的机制不同，不能直接比**：文献里的衰减是**依赖漂移、跨年发生**；
本项目是**同一台机器、同一环境、几天之内**。**唯一那次失效也不是环境造成的，
是我们自己的第八个里程碑删掉了第七世界判据引用的部件。**

所以这个 7/7 说明的是：**在环境不变的前提下，冻结判据 + 确定性种子确实撑得住。
它没有说明本项目能扛住跨年的依赖漂移**——那从未被测过。

## 3. 起草期做对的一个区分

goal 里我把两个问题混成了一个，design 阶段分开：

| | 能不能保障 |
|---|---|
| **归档复现**：当时那次运行能不能重放 | **能**——`git checkout <冻结 commit>` + 冻结种子 |
| **当下有效性**：今天的代码是否仍满足当时的判据 | **不能，也不该**——系统变了，结论本就该重判 |

**本里程碑测的是第二个。**

## 4. 四态，不是二态

`seventh` 那个不是「值变了」，是**判据在今天的代码上根本解析不了**。两者性质不同：

| 态 | 含义 | 是不是故障 |
|---|---|---|
| `reproduced` | 逐字节复现 | 否 |
| `value_changed` | 跑得通、答案变了 | **不是**——系统演化，结论过期是正常科学结果 |
| `unevaluable` | **问题没了**，判据引用的对象已被删除 | **是** |
| `unrunnable` | 跑不起来 | 不计入 H0 |

**把「答案变了」记成「坏了」会把正常的科学演化误判成故障**，所以预注册把两者混淆列为 IC-2。

## 5. 顺带测到的归档缺口（与 H0/H1 分开）

八份产物里 **6/8 记了自己的冻结 commit**；`second` 与 `fifth` 没记，要靠翻文档才能
定位冻结点——**归档复现（§3 左栏）对这两个不是一条命令**。种子只有 `third`/`fourth` 记，
但 `sixth`–`ninth` 是确定性审计、本无种子，不算缺口。

## 6. 负控

四态里的三个都实测翻转过：

- 把 `ninth` 的冻结产物改一个字节 → **`value_changed`**，verdict 转 H0
- 给 `sixth` 的 runner 加一行 `raise` → **`unrunnable`**，verdict 转 INVALID（**不计入 H0**）
- `unevaluable` 由 `seventh` 实时演示

恢复后两者均回到 `reproduced`，verdict 回 H1。

## 7. 事后更正：这个里程碑测的框架错了（2026-09-03，用户指出）

**verdict（H1，7/7 复现）不变，错的是我给它的解释。**

我把「今天的代码是否仍满足当时的判据」当成了一个需求。**它不是。** 一份 verdict 是
关于**某个时刻的系统**的断言；代码变了，它不再描述今天的代码——**这既不是故障，
它也从未如此声称**。据此把 `seventh` 记成「坏掉的判定」是误诊。

### 真需求只有一条

> **依赖未变时，verdict 必须逐字节复现。** ——这是确定性回归检测。

### 真原因：依赖未声明

`fourth` 的代码被第八个里程碑**大改过**（删掉整个类），它的 verdict **却复现了**
——因为**第八个里程碑自己的判据 C3 就要求保住它**。

`seventh` 坏掉，是因为它的产物**也依赖** `mechanisms/fourth_world/world.py`，
**而没有任何东西要求第八个里程碑保住它**。

> **一次改动只被要求保住它自己那个世界的产物。产物之间的依赖是隐式的，
> 所以没人知道还该检查谁。**

### 已修

`verdict_rot.py` 增加 `DEPENDS_ON` 声明与两条命令：

- `dependencies_changed(world)` —— 依赖自该 verdict 产出以来变没变。
  **未变 = 必须复现**；变了 = 只有那次改动自己声明保住它时才要求
- `impacted_by(paths)` —— 改了这些路径，哪些 verdict 必须被保住。
  **复验：喂给它 `fourth_world/world.py`，它列出 `fourth` / `eighth` / `seventh`
  ——正是第八个里程碑漏掉的那一个**

### 顺带：同一个坑第三次

首版用预注册的冻结 commit 做基准——**那个 commit 在 exloop，newlife 里解析不了**，
`git log` 返回非零，而我的代码把它当成「没有变动」，于是 `seventh` 显示「依赖未变」。
第八个里程碑踩过这个坑（IC-1）、写进了 skill，**记录没能阻止我再犯**。

已改用**本仓**产出该 summary 的 commit，并**解析失败一律硬失败，不退回「没变」**。
`silent_degradation_scan` 抓不到这一类——**它只认正则失败，不认 subprocess 失败**。
